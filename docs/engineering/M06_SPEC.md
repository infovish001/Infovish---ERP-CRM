# M06 Finance and Accounting baseline

Authorized by continuation after verified M05, implemented 2026-10-31. Stop before M07. Refines grouped FIN/BR-FIN/AC-FIN, E2E-006/007/010/019, NFR consistency/precision/isolation/audit and SAD Finance ownership. These acceptance labels are engineering refinements, not invented individual PRD IDs.

1. Bundled Finance, schema 5, depends on Parties/Sales public contracts. Owners/administrators with MFA mutate; granted-company auditors read; ordinary members cannot read Finance. No default real chart, mapping, tax registration, period, bank balance or transaction is fabricated. LKR functional currency only.
2. Explicit accounts (asset/liability/equity/income/expense, optional asset bank flag), non-overlapping date periods and reasoned locks. Account code/type/bank role is stable; names/active status are revisioned. Required receivable/payable/revenue/expense/input-VAT/output-VAT mappings are validated by type and frozen after the first posting. Fiscal years, closing entries, FX/consolidation, budgets/assets/treasury remain future work.
3. Draft manual journals hold 2-100 explicit cent-precision debit/credit lines. Server and deferred database constraints require positive equal debit/credit totals, one positive side per line, valid same-company accounts and an open posting period. Posted headers/lines are append-only. Corrections to manual journals use one reasoned opposite journal in an open period, retaining the original. Automatic invoice/payment journals cannot be reversed with the manual route. Manual AR/AP control postings are blocked to preserve subledger reconciliation. Operator opening balances must use supported documented migration workflows; no guessed opening balances.
4. Full customer invoice drafts come from one immutable confirmed Sales order via an authorized billing DTO. No partial billing/repricing. Bills are explicit supplier documents with unique supplier reference and operator-verified net/recoverable-input-VAT amounts; nonzero recoverable VAT requires an evidence declaration, not inferred eligibility. Posting creates an immutable journal, number, document snapshot, audit/outbox and permanent source link atomically. Draft updates require revisions; posted documents cannot edit/delete/cancel. Statutory credit/debit notes and returns require later reviewed workflows, not silent cancellation.
5. Ordinary domestic VAT18 tax invoices only: all lines standard-rated, actual registered seller and registered purchaser TIN/address, confirmed written-request evidence, supply date within 28 days and not future, issue/post date today. Seller details must match the Sales snapshot; no stale registration repricing. Commercial non-tax invoices support unregistered/exempt/zero-only orders but cannot conceal positive VAT; mixed/other regimes are rejected. Sales six-place inputs and cent totals are preserved. Invoice serial uses YYMMM_issuer-code_continuous-numeric-series, max 40 characters, code 1-15 alphanumerics with a digit, no silent reset; dates render MM/DD/YYYY, LKR amounts to cents. No general Sri Lankan tax compliance certification. See M06_TAX_REVIEW.
6. PDF issue is an authenticated CSRF-protected audited operation: one original issuance record, supplier duplicate and reasoned COPY ONLY requests, stable idempotent retries. Fixed escaped templates, no remote/PHP/JavaScript, no sending. Retain immutable snapshots and print history; production retention/restore remains a release gate. Actual supply-time determination and eligibility are operator assertions; special valuation, financial VAT, SSCL/withholding/imports/filings excluded.
7. Record partial/full receipts or supplier payments against one posted document in the same company, with explicit bank account/date/reference. Reject overpayment, wrong direction and closed periods; no external money transfer. Each record atomically posts bank↔AR/AP journal. Reasoned payment void adds an opposite journal and append-only void link; settled/reconciled entries cannot be silently removed. Outstanding amounts derive from effective payments. No gateway/bank integration or automatic settlement.
8. Manual bank statements have dated signed lines and explicit one-to-one ledger-line matches. All amounts/signs/account/company/date and global matching uniqueness are checked. Finalize only when opening + statement lines = closing and adjusted book balance reconciles exactly; no balancing plug. First statement requires explicit cleared-opening assertion and matching book opening; outstanding pre-baseline items are not supported. Subsequent openings equal the prior closing and statements advance chronologically; prior unmatched book lines can clear later. Finalized statements/matches are immutable. Backdated postings into a finalized bank window are rejected. Charges require separate authorized journals.
9. Posted-only trial balance, account ledger, income/expense period summary, financial-position snapshot including cumulative unclosed result, receivable/payable aging by due date. Exact decimal strings; reports are management views, not full statutory financial statements or automatic recognition policy. Bounded pagination/export limitations explicit. Transactions and reports are company/tenant scoped; financial data and private fields never enter queues/logs.
10. Host/container/PostgreSQL/Redis tests cover balance/locks/reversals, source idempotency/concurrency, rollback, payment allocation/void/reconciliation, reports, tax/PDF/numbering, permissions/CSRF, schema upgrades and immutable guards. Frontend tests/type/lint/build, fresh-cache format/static/boundary/API/audit/secrets, real synthetic browser/PDF checks and hosted CI required. Actual local schema upgrade preserves existing data and leaves Finance inactive/empty. R1 remains unreleased until documented production/localization/security/recovery/load gates close.
