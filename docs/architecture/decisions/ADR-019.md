# ADR-019 M02 verified tenant execution and identity

Date: 2026-10-30. Status: selected for the authorized M02 baseline.

Use platform-owned identity/membership and exact domain registration, with separate PostgreSQL databases and least-privilege application roles per tenant. Web and worker processes use the platform application role; an operator CLI uses separately supplied provisioning credentials. Runtime tenant credentials are encrypted in the registry. Scoped connections never replace the default platform connection.

Use Laravel Fortify for login/password confirmation/TOTP. Require MFA for owner/administrator workspace access. Bind host-only sessions to tenant identity and user session version. Company/branch grants are explicit for non-privileged users. Audit history is append-only at PostgreSQL and application privilege layers.

Alternatives: per-tenant identity duplicates accounts and complicates revocation; shared business tables increase the accidental-leak surface; custom authentication cryptography adds unnecessary risk. The selected design incurs platform lookups and a bounded per-process tenant connection. Measure pooling and fleet migration capacity before commercial scale; M02 does not establish enterprise capacity guarantees.

Migration: add platform identity/registry tables without changing M01 data. Provision tenant databases through versioned tenant-only migrations. Preserve partially provisioned resources on failure and retry the same registry identity; never recreate a database merely because a command failed. Test on dedicated ephemeral databases/roles and preserve existing development data.

References: PRD TEN/IAM/ORG ranges, BR-TEN, SAD sections 4/10, ADR-004/005, M02_SPEC.md and [Laravel Fortify](https://laravel.com/docs/13.x/fortify). Mail-dependent account recovery and enterprise SSO require separate delivery/security configuration and are not claimed complete.
